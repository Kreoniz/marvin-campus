# Карточки занятий: mobile, подгруппы и общие пары

Дата: 2026-10-20–21. Исследование локальной React-версии, без изменения приложения.
Независимый анализ: Astra 6, reasoning xhigh; сопоставление с кодом и браузером.

## Что проверено

- В `src/features/schedule/ui/Calendar.tsx` ширина карточки ограничена 160 px,
  но `left` рассчитывается как доля полной ширины дня. Ограничение ширины не
  ограничивает расстояние между началами карточек.
- При ширине viewport 430 CSS px у выбранного дня ширина 373 px. Две вечерние
  карточки имеют ширину 160 px, начала x=35 и x=221: зазор 26 px. При viewport
  390 px ширина дня 336 px, зазор около 7.5 px. Это измерения одного расписания,
  а не универсальные размеры для любого экрана.
- `src/lib/lesson-layout.ts` назначает колонки пересекающимся событиям,
  а не группам; отдельные компоненты пересечений получают собственное число
  колонок. Одна группа не обязана оставаться на одном месте в течение дня.
- Внутри одного блока пересечений `columns` общее даже при цепочке частичных
  пересечений. Нельзя независимо двигать карточки каждой произвольной строки
  без учёта длинных событий.
- Одно подтверждённое событие нескольких групп объединяется в карточку с
  `members`. `common` дополнительно означает всех выбранных участников при
  полных данных. Похожие названия и время не доказывают совместность.
- Полосатые `parallel`-карточки означают разные события одной группы с точно
  совпавшими интервалами. Это не обязательно две подгруппы; возможно сочетание
  общегруппового события, лабораторной и пересдачи.
- `src/lib/subgroups.ts` выводит принадлежность занятия по данным источника,
  независимо от выбранного фильтра. Общегрупповая пара не превращается в `/2`
  при выборе второй подгруппы.
- `src/lib/colors.ts` сохраняет назначенные группам цвета. Опубликованные стили
  unlikely-ui содержат шесть `--u-category-*`, но не токены оттенков подгрупп.
  В `LessonCard.tsx` приглушение уже используется для сохранённых данных.
- Дополнительно открыты реальные общие лекции 21 октября при четырёх выбранных
  группах. В карточке 160 × 55.5 px читаются три секции по 52 px: МО-231,
  ФИТ-231, ФИТ-232. Они представляют часть выбранных групп. Сам по себе этот
  пример не доказывает, что замена секций строкой будет улучшением.

## Рекомендация 1: компактная упаковка карточек

Сохранить максимум 160 px и постоянный небольшой зазор 6–8 px. Ограничить не
только ширину карточки, но и шаг колонок внутри компоненты пересечений.
Для текущих отступов кандидат: шаг `min(W / n, 166)`, ширина
`min(W / n - 6, 160)`, начало `3 + column * шаг`. Это предложение геометрии,
не реализованный код. Все карточки одной компоненты используют одно правило.

Одиночная карточка остаётся компактной. Две стоят рядом; свободное место
остаётся справа. Три сжимаются при недостатке ширины. Вертикальная координата
и высота продолжают выражать время и длительность.
Ограничение не следует переносить на горизонтальную шкалу выбранного дня:
там ширина означает длительность.

Ожидаемая польза: устраняется подтверждённый лишний зазор; решение близко к
понравившемуся desktop-примеру. Оно не создаёт постоянные колонки групп.
Не доказано пользовательским тестом, что это предпочтительный вариант для
всех расписаний. Сложность небольшая: геометрия, проверки пересечений,
длинных событий и обеих ориентаций. Дизайн-систему менять не требуется.

### Почему не другие варианты по умолчанию

- Растянуть одиночную карточку на весь день: пользователь уже отверг этот
  вариант. Больше текста видно, но слишком большая заливка и разные размеры.
- Растягивать только несколько одновременно идущих карточек: допустимая
  альтернатива для сравнения на макете; убирает зазор ценой большей вариации
  ширины между двумя и тремя событиями. Не первая рекомендация.
- Использовать максимум колонок за весь день: выравнивает ширины, но один
  плотный эпизод с тремя событиями сужает и одиночную утреннюю, и две вечерние.
- Отдельная колонка каждой группе: легче отслеживать группу, но четыре
  выбранные группы требуют четыре колонки даже при трёх одновременных
  событиях; появляются пустые места и горизонтальная прокрутка. Общая пара
  несоседних групп требует отдельного решения, иначе span намекает на лишних
  участников или дублирование выглядит как несколько занятий.
- Лимит видимых событий и «ещё N»: существующий календарный паттерн, но скрывает
  занятость, важную для сравнения. Не предлагать по умолчанию.
- Список дня: возможный отдельный режим для чтения предметов; хуже показывает
  одновременность и свободные промежутки. Не заменять им календарь автоматически.

## Рекомендация 2: общие пары и параллельные события

У подтверждённого общего события оставить одну карточку, нейтральный фон,
один предмет и аудиторию. Кандидат для сравнения с текущим вариантом:
цвета участников показать узкой сегментированной полосой, а имена — цельными
подписями. Разрыв `ФИТ` / `231` можно убрать там, где хватает ширины; в узком
варианте он помогает вместить больше подписанных участников. Astra отдельно
оспорил безусловную замену секций строкой: это не проверенное улучшение.

В доступной ширине показать максимально читаемое число участников. Кандидаты:
две подписи плюс `+N`; одну плюс `+N` использовать лишь при нехватке места.
Полный список — по нажатию. Ограничение зависит от ширины, а не только числа
участников. Различать «3 из 4» и «Все 4», не добавляя новый ряд поверх всего
текущего содержимого. «Для всех выбранных» допустимо только при `common`.
Недоступные данные не позволяют делать вывод об участии всех.

Не смешивать оттенки участников в один усреднённый цвет; не использовать
зелёную заливку, означающую свободное время. Не переносить длинное общее
занятие в условный all-day блок: это теряет представление его занятости.

У `parallel` оставить явное «2 занятия» / «2 занятия одновременно» и понятный
признак нескольких событий. Кандидат вместо яркой сплошной штриховки —
небольшой значок стопки и спокойный фон; это эстетическая гипотеза. Если места
достаточно, показать «Лаб + пересдача» или достоверные номера подгрупп.
Не объявлять все такие карточки конфликтом: события могут относиться к разным
подгруппам. Не выдавать весь bundle за одну подгруппу. В подробностях каждое
исходное событие сохраняет свой предмет, тип, аудиторию и принадлежность.

Сложность средняя: единая иерархия обычных/shared/parallel-карточек,
адаптация к ширине и длинным занятиям, сохранение доступных подписей и статусов.
Конфликта с DS нет: нейтральные поверхности и существующие категориальные
цвета. Это собственный доменный компонент приложения, не замена DS-контролов.

## Рекомендация 3: необязательные оттенки подгрупп

Идея разумна как выключенная по умолчанию настройка «Различать подгруппы
оттенками». Особенно полезна при просмотре всей группы, где одновременно
видны `/1` и `/2`. Разместить в настройках вида, не рядом с основными режимами
«В вузе» / «Без занятий». Выбор можно хранить локально; это не фильтр данных.

- Сохранить базовый цвет группы. `/1` и `/2` получают близкие, но различимые
  варианты того же цвета; номера остаются видимыми.
- Общегрупповое занятие сохраняет базовый вариант независимо от фильтра.
- Неизвестная или множественная принадлежность не получает произвольный оттенок
  первой подгруппы; сохранить базовый вариант и достоверную подпись.
- В общей карточке оттенок применим к метке конкретного участника, а не всей
  нейтральной поверхности. У parallel — к конкретному событию в подробностях.
- Не менять `opacity`: приглушение уже связано со свежестью. Проверить также
  сочетание оттенка с сохранёнными данными и обеими темами.
- Проверять текст на каждом фоне. Минимум для обычного небольшого текста —
  4.5:1. Не обещать отдельный норматив 3:1 между всеми оттенками, если смысл
  полностью продублирован видимыми номерами.

Сложность небольшая/средняя: настройка, производные цвета по достоверной
принадлежности, проверки комбинаций. DS не даёт готовых токенов подгрупп:
потребуется осознанное расширение категориальной палитры или документированное
производное значение в приложении. Это не повод вводить независимые цвета
вместо стабильных цветов групп. Приоритет ниже геометрии и общих карточек.

## Дополнение: присутствие, нажатие на карточки и шапка

### Заметность «В вузе»

Сравнение с `main` (`af9739f`) подтвердило смену оформления при миграции:
в Svelte `Calendar.svelte` использовал yellow 18% и отдельную жёлтую границу;
`DayDetail.svelte` — yellow 25%. React Calendar и DayDetail используют muted 8%
и обычную границу `--u-line`. В легенде presence теперь `--u-well`.

В браузере на тёмной теме: поверхность `#2c322b`, скомпонованная заливка
`#363d35`, различие яркости примерно 1.17:1. Это измерение поверхности без
линии сетки, а не заявление о нарушении WCAG. Astra отдельно проверил
объявленные старые CSS: в тёмной теме прежняя заливка была заметнее по яркости,
но в светлой нельзя утверждать то же для всех сочетаний. Потеря жёлтого
цветового различия подтверждена в обеих темах.

Рекомендация: вернуть отдельное янтарное обозначение присутствия с согласованными
fill, edge и legend; зелёный сохранить за свободными промежутками. Не копировать
старый цвет границы вслепую: для светлой темы нужна более тёмная янтарная
граница, для тёмной — светлая. Это доменные токены приложения или осознанное
расширение DS, а не warning/error-состояние.

Отдельно согласовать сохранённые состояния: Calendar заменяет заливку на muted
5%, а DayDetail сохраняет заливку режима и добавляет dashed. Это расхождение
представления, не расчёта времени. Сложность небольшая/средняя с проверкой
обеих тем и сохранённых данных; приоритет выше новой опции оттенков.

### Почему двигается пара при нажатии

В `LessonCard.tsx` явно задано `active:translate-y-px`. Проверено trusted-click
в браузере при viewport 430 px: до нажатия y=422, на pointerdown y=423,
после pointerup y=422. Computed translate при нажатии `0px 1px`. Обёртка
оставалась y=422; scrollY=12, scrollTop календаря=0 и ширина документа=430
не менялись. В этом воспроизведении это эффект нажатия, не перераскладка.

Рекомендация: убрать перемещение у карточек календаря, сохранив статичную
подсветку/границу активного состояния и видимый клавиатурный фокус. Геометрия
занятия на временной шкале должна оставаться неподвижной. Изменение небольшое,
DS не требует данного transform: это прикладной Tailwind-класс.

### Почему «42» не у правого края

В `SiteHeader.tsx` описание имеет `mr-auto`, а блок действий — `ml-auto`.
Два auto margin делят свободную ширину. На viewport 1280 px браузер показал
221 px у каждого отступа; декор заканчивается на x=920, а действия начинаются
на x=1157. Между ними остаётся 237 px с учётом обычного gap.

Минимальное предложение: заменить `ml-auto` действий на `compact:ml-auto`,
оставив desktop-распределение описанию. Тогда декор и действия соседствуют
справа, а мобильные действия по-прежнему прижаты вправо при скрытом описании.
Альтернатива — единая правая группа с одним auto margin. Это flex-layout
приложения, не сбой Badge/Button или reset дизайн-системы. Сложность небольшая.

Ни одно из этих предложений не применялось к приложению.

## Источники и пределы исследования

- Исходный код приложения: `Calendar.tsx`, `LessonCard.tsx`, `lesson-layout.ts`,
  `lesson-layout.test.ts`, `domain.ts`, `subgroups.ts`, `colors.ts`; продуктовые
  правила `docs/product.md`, `CONTEXT.md`; опубликованный CSS unlikely-ui.
- [FullCalendar: slotEventOverlap](https://fullcalendar.io/docs/slotEventOverlap)
  документирует варианты перекрывающихся/неперекрывающихся карточек. Это пример
  существующего паттерна, не доказательство предпочтительности и не рекомендация
  устанавливать эту библиотеку.
- [FullCalendar: eventMaxStack](https://fullcalendar.io/docs/eventMaxStack)
  документирует скрытие избытка событий за счётчиком с поповером. Для сравнения
  занятости этот паттерн несёт описанную выше потерю видимости.
- [FullCalendar: Vertical Resource View](https://fullcalendar.io/docs/vertical-resource-view)
  показывает ресурсы отдельными колонками; оценка пригодности для групп здесь
  является проектным суждением, не выводом документации.
- [W3C: Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
  требует не передавать смысл только цветом; номера подгрупп и текстовые подписи
  должны сохраняться.
- [W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
  задаёт 4.5:1 для обычного текста и исключения для крупного текста.
- [W3C: Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
  описывает значимые части графики и возможность обозначить форму контуром;
  низкий контраст отдельной фоновой заливки сам по себе не доказывает нарушение.
- [CSS Flexbox: auto margins](https://www.w3.org/TR/css-flexbox-1/#auto-margins)
  описывает распределение свободного места между автоматическими отступами.

Проверены исходники, два пользовательских изображения, текущая геометрия в
браузере на viewport 390 и 430 CSS px и реальные общие карточки на 21 октября.
Для дополнения проверены CSS исходного Svelte main, React-код, trusted-click
на 430 px, вычисленные цвета и геометрия шапки на 1280 px.
Визуальная схема предложений отдельно
проверена на 360 и 728 px, включая переключение разделов и настройку оттенков.
Это не пользовательское исследование, не тест на физических устройствах и не
проверка новой реализации. Рабочие компоненты приложения не изменялись.
